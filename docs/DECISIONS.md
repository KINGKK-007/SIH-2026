Format (README R6): `D-### · YYYY-MM-DD · Phase · what changed · why · impact`.
The v0 architecture decision records are archived in `archive/DECISIONS_v0.md`.

- D-003 · 2026-09-23 · 1 · Phase numbering and task IDs follow `docs/PHASES.md` (15 phases), which supersedes README Section 10 (Phases 0–8); checkboxes are ticked in `docs/PHASES.md` · the team works from the 15-phase plan · README "Section 10" references mean `docs/PHASES.md`.
- D-004 · 2026-09-23 · 1 · The v0 implementation (built from the earlier 9-phase master plan: float-metre grid, 17-byte cells, Streamlit/matplotlib demo) moves to `src/foveamap_legacy` with its 311 tests in `tests/legacy` instead of being deleted · the spec requires integer-mm addressing, 12-byte cells and a different module layout, but the v0 code is useful reference for motion, derived layers and hazards · legacy tests run in `make test`; lint/typecheck skip legacy; legacy is removed once every module is ported (target: Phase 15).
- D-005 · 2026-09-23 · 1 · One development machine is native Windows 11 (no WSL, no NVIDIA GPU, `mingw32-make` + Git Bash) rather than Ubuntu/WSL2 (README 4.1) · team split: GPU/data work runs on a teammate's machine · the Makefile and scripts are written to run on both; GPU checks are warnings on this machine.

- D-007 · 2026-09-23 · 1 · `requirements.txt` adds developer tools (ruff, black, mypy, pytest-cov, types-PyYAML) to the README 4.5 list · `make lint/format/typecheck` need them · slightly larger install.
- D-008 · 2026-09-23 · 1 · `requirements.lock` is platform-specific (it records the torch wheel of the machine that produced it) · one lock cannot serve Windows-CPU and Linux-CUDA · the lock header states its platform; other machines install from `requirements.txt` and may regenerate the lock.
- D-009 · 2026-09-23 · 1 · pytest runs with `--import-mode=importlib` · README 11.2 places same-named test modules in several subfolders (and `tests/legacy` repeats names) · no `__init__.py` needed in test folders.

- D-013 · 2026-09-23 · 3 · T3.3 label cross-check: README Appendix A was compared with `semantic-kitti.yaml` from PRBonn/semantic-kitti-api (commit a9c749e8124b, MIT, vendored at `src/foveamap/io/semantic-kitti.yaml`): all 34 raw IDs, names, `learning_map` and `learning_map_inv` agree exactly; no differences · required by T3.3 · the test suite re-checks this on every run.
- D-014 · 2026-09-23 · 3 · `Prediction.raw_ids` / oracle raw IDs use uint16, not uint8 (README 9.1) · moving IDs 256–259 do not fit in uint8, and the oracle preserves moving IDs · cached model predictions (static IDs <= 99) may still be stored as uint8 on disk.
- D-015 · 2026-09-23 · 3 · Added `foveamap/io/synthetic.py`: a seeded generator that ray-casts a 64-beam sensor through an analytic street scene and writes a complete SemanticKITTI-layout sequence (bin/label/calib/poses/times, non-identity `Tr`, camera-0 poses) · README 11.1 asks for a synthetic scan fixture, and one data machine means everything else must be testable without the dataset · synthetic data is used for tests and demos only; it never feeds a reported number.
- D-016 · 2026-09-23 · 3 · Distance buckets are half-open `[a, b)` except the last, which is closed (`[60, 100]`), so a point at exactly 100 m is counted; points beyond 100 m (square-grid corners reach 141 m) get bucket -1 · L16 names the buckets but not the boundary rule · per-bucket point metrics exclude horizontal range > 100 m; this is stated wherever buckets are reported.
- D-017 · 2026-09-23 · 2-3 · Phase 3 loaders (T3.1–T3.4) were implemented before the Phase 2 tools (T2.2, T2.3), which reuse them · avoids duplicating calib/pose/label parsing in scripts · Gates 2 and 3 are both run on real data once it is available (teammate's machine).
- D-018 · 2026-09-23 · 4 · T4.1 gate strengthened: besides the specified median NN on building/road/vegetation (< 0.15 m, kept), Gate 4 also requires the median NN on compact structure (pole, trunk, traffic-sign) < 0.15 m and requires the identity "no transform" control on moving pairs to *fail* that threshold (otherwise the verdict is INCONCLUSIVE) · measured on the synthetic sequence, the specified class set alone accepts wrong transforms: identity 0.012 m, inverse 0.045 m, correct 0.038 m, because flat-road LiDAR rings move with the sensor and facades are parallel to the motion; on compact structure correct is ~0.03 m and every wrong variant (identity, inverse, missing or swapped Tr conjugation) is >= 0.74 m · stricter gate (R2 forbids weakening, not strengthening); the real-data verdict is produced on the teammate's machine.
- D-019 · 2026-09-24 · 5 · Grid accumulators are stored sparse (sorted unique flat cell indices + one array per field) instead of dense arrays over each ring's full square (README 9.5); `RingAccumulators.to_dense()` gives the dense view · a dense `uniform_5cm` accumulator set is ~700 MB per frame and allocating ~1.1 M-cell dense arrays per frame costs more than the whole grid budget, while occupied cells never exceed the point count; the 12-byte packed layers (the memory figure, L10) remain dense per ring · all invariant tests run on the sparse form (bit-exact); the uniform-5 cm reference is sparse as README 12.4 already requires.
- D-020 · 2026-09-24 · 5-7 · Phases 5-7 (grid engine) are built before Gate 4 passes · Gate 4 needs the real dataset (teammate), and the grid engine is independent of it (README 0.4 already allows Track A to proceed from Phase 1) · Gates 5-6 are self-contained; Gate 7's real-data render/timing commands run on the data machine.
- D-021 · 2026-09-24 · 6 · Class-rule tie-breaks: safety rule's ground argmax resolves ties NON_DRIVABLE_TERRAIN > UNKNOWN > DRIVABLE (so a cell with no qualifying class and no ground points becomes NON_DRIVABLE_TERRAIN); majority rule resolves DYNAMIC > STATIC_OBSTACLE > NON_DRIVABLE_TERRAIN > UNKNOWN > DRIVABLE; fraction thresholds are compared exactly as rationals; moving_frac and conf use the same integer half-up rounding as ground_z; `clearance` equals the gap when gap >= contact height (gap == 0.30 m counts as overhang) · README 6.6 says "ties resolve to the more conservative class" without an order, and "unknown is not free" (6.7) · deterministic, documented class output at every resolution.
- D-022 · 2026-09-25 · 8 · README L11 overridden: the production segmentation model is **LSK3DNet** (CVPR 2024 sparse large-kernel voxel network, pretrained on SemanticKITTI, 75.6% mIoU val), not a range-view network (SalsaNext/CENet/RangeNet++) · a pretrained LSK3DNet checkpoint was supplied for this project and the team chose to use it directly instead of running the range-view Model Selection Gate (T8.1) · `configs/model.yaml` gains `family: sparse_voxel` and an `lsk3dnet:` section (`src/foveamap/config.py: LSK3DNetConfig`); the wrapper is `src/foveamap/models/lsk3dnet.py`; `models/rangeview.py` stays a stub, kept only for the T9.4 "why not range-view" comparison; T9.4's framing inverts accordingly (justify the heavier sparse-voxel choice against a lighter range-view alternative, not the reverse). mIoU/latency numbers are not filled in here (R1); they come from running T9.3/T9.4 on the GPU machine.
- D-023 · 2026-09-25 · 8 · `lsk3dnet.vram_budget_gb` in `configs/model.yaml` targets 6 GB (a teammate's RTX 4050 laptop), not the 4 GB RTX A500 Laptop GPU on this dev machine (`torch.cuda.get_device_properties(0).total_memory` measured 4.29 GB here) · same split as D-005 (GPU/data work runs on a teammate's machine); the two GPUs were confused once in conversation and corrected · `LSK3DNetModel` always runs batch-of-one with no TTA voting and an optional fp16 autocast forward pass regardless of which of the two GPUs it runs on, so it is not tuned specifically to either; `scripts/cache_predictions.py` (T9.1, full sequences 04/07/08) is expected to run on the RTX 4050, not this machine.
- D-024 · 2026-09-25 · 8 · `LSK3DNetModel.predict` never feeds points outside the checkpoint's own training crop (its config's `dataset_params.min/max_volume_space`, ±50 m in x/y and [-4, 2] m in z) into the sparse-conv stack; those points are returned as `UNKNOWN` with `conf = 0` instead of a model prediction · the crop is narrower than the FoveaMap grid extent (±100 m, L4), and feeding out-of-crop points would produce out-of-range voxel indices (a crash), not a meaningless-but-harmless prediction · the 60-100 m distance bucket's model accuracy (T9.3) is mechanically capped by this crop and must be reported as such, not blended away; a warning is emitted per `predict()` call listing how many points were affected.
- D-025 · 2026-09-25 · 8 · `LSK3DNetModel` imports the vendored `LSK3DNet-main/` checkout in place (`sys.path` insertion cached per-process) rather than vendoring a copy under `models/third_party/` as T8.2 suggests · the checkout (~30 files) is already at the repo root and duplicating it under `src/` would drift out of sync · two consequences logged here so they are not rediscovered the hard way: (1) LSK3DNet pins `torch==1.11.0+cu113`/`spconv-cu113`, which predate the Ada Lovelace RTX 40-series (and do not recognise this dev machine's Ampere RTX A500 either); both GPU machines need current CUDA-version-matched `torch`/`spconv`/`torch-scatter` wheels instead (`docs/MODEL_CARD.md` has the commands). (2) LSK3DNet's per-point normal feature needs the vendored `c_utils` pybind11 extension (`c_gen_normal_map`); the repo's Python fallback is commented-out dead code, not a working path, so the extension must be compiled on every machine that runs live/caching inference (`docs/MODEL_CARD.md` has build steps); `models/cache.py` (T9.2, no GPU) is unaffected.
